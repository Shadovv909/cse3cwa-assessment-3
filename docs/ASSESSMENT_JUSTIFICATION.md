# Assessment Task 1 Verbal Justification

Phoneme Studio is designed as a teacher-facing authoring application rather than a client treatment portal. My main goal was to make the route from a teaching idea to a usable classroom resource obvious: configure an activity, test the live preview, and generate one standalone HTML file. Both builders use this same workflow, which reduces the interface knowledge a teacher must remember. The Home page introduces the project and links directly to each tool. The About page explains the current frontend scope and makes it clear that accounts, persistence, and database-backed generation belong to later assessments.

The visual design uses calm blue-green surfaces, restrained accent colours, rounded panels, readable typography, and generous spacing. Numbered form sections and clear status panels divide long authoring tasks into manageable decisions. On wide screens, controls and previews sit side by side so changes can be inspected immediately. The Wordle keyboard also sits beside its board, following the supplied activity guidance. At narrower widths the builders stack, grids remain inside scrollable local containers, and full navigation changes to a compact kebab menu. This preserves access to Home, Wordle, Word Search, About, and Settings without causing page-level horizontal overflow.

The supplied broad HCE material is treated as the source of truth. The authoring palette contains the complete 43-symbol inventory, and the project includes all 90 supplied examples: 30 words with three phonemes, 30 with four, and 30 with five. Multi-character phonemes such as `/tʃ/`, `/dʒ/`, and `/æɪ/` occupy one cell rather than being split into letters. The Wordle builder groups all corpus examples by phoneme count, while Word Search provides five-word sets for three-, four-, and five-phoneme practice. Teachers can still edit the activity manually, so the corpus supports fast setup without becoming a database feature outside the assessment scope.

The Wordle activity operates on phoneme sequences rather than spelling. A teacher chooses an English answer, target sequence, attempt limit, difficulty, and hint setting. Guided mode reduces distractors, Standard adds discrimination choices, and Challenge exposes the complete HCE keyboard. The preview uses duplicate-aware scoring so repeated phonemes are not over-counted. Correct, present, and absent results combine colour with tick, double-arrow, and cross symbols. Each key has a hover title and accessible name such as “/θ/ — TH (as in thin)”. The English equivalent appears after success or the final attempt, creating a clear activity conclusion.

The Word Search builder manages a short editable list and generates a grid without a database. Its bounded backtracking algorithm places longer sequences first, favours legal overlaps, and retries candidates deterministically from a seed. Guided mode uses horizontal and vertical directions, Standard adds diagonals, and Challenge adds reverse placement. Crucially, the game stores intended coordinates rather than accepting any accidental matching filler sequence. Students select the first and final tile, and the line is checked in either reading direction against an unfound placement. Found cells, the target list, and the live message all update together. Escape clears a starting tile, and normal buttons make the interaction usable by keyboard, mouse, or touch.

Component architecture is part of the design. The shared app shell owns the skip link, header, main landmark, and footer. Builders manage teacher configuration, while separate preview components manage temporary student game state. The phoneme palette and page heading are reusable UI components. Scoring, keyboard construction, grid placement, filename handling, downloads, and complete HTML generation live in focused utility modules. Shared TypeScript types describe activity settings, corpus words, coordinates, placements, and tile results. This separation reduces duplication and gives later assessments clear extension points for saved activities, APIs, or a larger word service.

Accessibility is integrated rather than added at the end. Inputs have visible labels; related choices use fieldsets; status changes use polite live regions; focus outlines remain visible in both themes; and controls are sized for touch. Wordle never relies on colour alone. Word Search cells announce row, column, phoneme hint, and found state. The interface respects reduced-motion preferences and provides a skip link. Automated axe-core checks reported no WCAG 2.0 or 2.1 A/AA violations on the five desktop pages, representative mobile pages, or the two standalone examples. Browser checks also confirmed no mobile overflow and no console errors during the tested workflows.

Settings demonstrate persistent frontend preferences without expanding the data scope. Light/dark theme and comfortable/compact density are stored in first-party cookies. An inline initialisation script applies saved values before the React interface becomes visible, reducing theme flash. Activity content stays in component state and is not sent anywhere. The chosen theme is included in generated activities, so the exported presentation reflects the teacher’s selection.

The single-file export requirement influenced the technical design. Each export function builds a complete HTML document containing metadata, responsive CSS, escaped teacher text, safe JSON activity data, and plain JavaScript. A browser Blob and temporary download link produce the file without an API route. The verified examples contain no external scripts or stylesheets and remain playable when opened directly. This makes them practical for a classroom computer or learning platform while keeping the Next.js builder maintainable.

The main limitation is deliberate: the corpus is static and activities are not saved between sessions. Assessment 1 prioritises frontend quality, usability, accessibility, and reusable structure rather than persistence. The result is therefore a polished foundation that satisfies the present brief and can later accept database-backed lists, teacher accounts, and advanced generation without replacing its core workflow.
